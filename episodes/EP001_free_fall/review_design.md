## 2. 計測の前に片づける条件

### K1. 計測したサーバの版を、サーバ自身の出力で run フォルダに残す

- 場所: `lab/runner.py` の `meta.json`（`mc_version` は `--mc-version` の引数をそのまま書くだけ）、`orchestra/pipeline.yaml` の measure（episode.yaml の値を引数に入れる）、`mc/server/README.md`（例が `--mc-version 1.21.x`、Java 21）。
- 問題: 結果に付く「26.3」は、どこでもサーバに問い合わせていない。置いてある jar が 1.21.11 や 26.1 でも、ゲームルール名が通れば確認項目は全部合格し、結果は「26.3 の【実測】」として knowledge と台本に流れる。
- 視聴者が持つ誤解: 画面の緑ラベル「MCの仕様 26.3」を見て、その版で測った値だと信じる。CLAUDE.md の「物理の挙動はバージョンで変わる」に当たる。
- 止める指摘にしない理由: 設計の物理は変わらない。計測の担当が1行残せば足りる。
- 直し方の案（どれか1つ）:
  1. サーバ起動ログの版の行（`Starting minecraft server version …`）を run フォルダに保存する。
  2. runner が setup で `version` コマンドを送り、応答を `commands.jsonl` に残す（バニラに `version` コマンドがあるかは【未確認・審査者の記憶】）。
  3. analyze が、残した版と experiment.yaml の `mc_version` が違えば「結論を出さない」にする。
- あわせて `mc/server/README.md` の例を 26.3 に直す（mc の担当。26.x に要る Java の版も【未確認】）。

## 3. 止めない指摘

計測の質を上げるもの:

1. **生物の g は、ゲームに直接聞ける可能性がある。** 1.20.5 以降、生物の重力は属性になっている【未確認・審査者の記憶】。`attribute @e[tag=track_pig,limit=1] minecraft:gravity get` が 0.08 を返せば、地球比①は「当てはめの計算値」ではなく「ゲームが返した値【実測】」になる。豚・牛・アーマースタンドに1回ずつ足す価値がある。
   - 属性なら個体ごとに変えられる。「種類で決まる」は正確には「種類ごとの既定値で決まる」。台本の言い方に効く。
2. **「1ブロック=1 m」「20 tick/s」は、前提のままにしなくてよい可能性がある。**
   - 統計画面の移動距離は cm 単位（`walk_one_cm` など）で、1ブロック歩くと 100 cm 増えるはず【未確認・審査者の記憶】。実機で確かめれば「ゲーム自身が1ブロックを 1 m と数えている【実測】」と言える。
   - `tick query` の応答（目標 20 tick/s と実際の tick 時間）を通常速度の確認のときに残せば、「20 tick/s」もこのサーバの実測になる。サーバが重いと秒への換算がずれる。
3. **`landing_gap` は「計測値だけで判定」ではない。** 次の1tickの移動を |Motion.y − g| で出すとき、g に `mc_constants.yaml` の予想値を使っている（`analyze_track`）。差は最大でも 0.04 ブロック程度で、判定は変わらない。直前の1tickの実際の移動（Pos の差）を下限に使えば予想値が要らなくなる。
4. **落下ブロックとアイテムの比較（across）は、丸めの差で「不一致」になりうる。**
   - 生物の抵抗は単精度（0.98000002）、落下ブロックとアイテムは倍精度のはず【未確認・審査者の記憶】。落下ブロックとアイテムの片方だけが単精度なら、y の差は 1e-5 ブロック程度になり、1e-9 の基準で「不一致」になる。着地 tick は同じ。
   - `series_match` は空中の tick の集合も同じであることを求める。金床は消滅、アイテムは OnGround で判定するので、判定が 1 tick ずれるだけでも「不一致」になる。
   - どちらも「結論を出さない」側なので止めない。不一致が出たら、summary.md の「y の最大差」と着地 tick を見て、「着地 tick は同じ。位置の差は○ブロック」と書き分ける。「落下ブロックとアイテムは別の動き」とは書かない。
5. **後片付けの `kill` で、豚と牛が肉や革を落とす**【未確認・審査者の記憶】。繰り返し3回と通常速度の1回で、着地点に溜まる。計測には効かないはずだが、タグがないので消えない。prepare にアイテムを消すコマンドを足すか、撮影の前に消す。
6. **コマンドの失敗の検出は、記憶で書いた文字列に頼っている**（model.md §2.4 に記載済み）。失敗の文字列を数える方式なので、知らない文面の失敗は「合格」になる。影響が残るのはゲームルールと時刻だけで、落下の結論には効かない。初回の実行で `commands.jsonl` を目で読む手順は必ず行う。
7. **3回の繰り返しが示すのは「同じ条件で同じ結果」まで。** 統計的に独立な3回ではない。台本で「3回測って確かめた」と言うと、ばらつきのある測定を平均したように聞こえる。「毎回 tick 単位で同じ結果になる」と言う。

撮影（experiment.yaml の shots）:

8. **`wide_side`（60ブロック離れた定点）では、アイテムが映らない可能性が高い。** 小さいエンティティは描画される距離が短い（アイテムは十数ブロック程度）【未確認・審査者の記憶】。256ブロックの落下全体も、この距離では画角に入らない。「金床のアイテムと羽根が同じ動き」は S1 の証拠の中心なので、映らないと視聴者には証拠が届かない。撮影の最初に確かめ、だめなら組ごとに近くで撮る（比べるショットは同じ再生速度で）。
9. **確認用のグラフ（`lab/plot.py`）は、そのまま動画に出さない。** 色が3色の使い回しで、種類と対応しない（金床と鉄インゴットが同じ色）。模擬サーバの結果でも凡例に「（実測）」と出る。動画用は movie 側で作る前提なので止めない。

台本へ渡す注意（final_review で確認する）:

10. **「地球の約3倍強」は、落ち始めの速度の増え方の話。** 256ブロックを落ちる時間から平均の加速度（2h/t²）を出すと、生物は約 17 m/s²（地球の約1.7倍）、落下ブロック・アイテムは約 6.6 m/s²（約0.7倍）になる（予想値からの計算）。落下ブロックは「重力が地球の1.6倍」なのに、256ブロックでは地球の真空より遅く着く。model.md §5 の10番と同じ論点。倍率を出す画面に「落ち始めの」を必ず入れる。
11. **生物の倍率を、位置から読むと合わない。** 生物は1tick目に動かないので、最初の数tickの位置から加速度を出すと 32 m/s² より小さく出る（3tick で約 21 m/s²）。視聴者が動画をコマ送りで確かめると食い違う。倍率の定義は「速度の変化」と画面に書く。
12. **プレイヤーは測っていない。** 視聴者がいちばん知りたいのは「自分が落ちるとき」。Wiki はプレイヤーを生物と同じ行に書いているが、E001 の対象は豚・牛・アーマースタンドだけ（model.md §4 に記載済み）。台本で「プレイヤーも」と言うなら、プレイヤーを測る（Carpet の偽プレイヤーが同じ計算かは【未確認】）。
13. **現実側の値がまだ全部【未確認】か【二次】。** g=9.80665 m/s²（割る側の数）、自由落下と終端速度の式、FAI の約200 km/h（本文未読）。台本で断言するには一次資料が要る（2回目から継続）。
14. **MC側の根拠は Wiki の【二次】だけ**（同上）。実測と食い違ったら、実測値を mc_version 付きでそのまま報告する。
