# 時間と tick（1秒20tick、1日24000tick、ランダムティック、処理の順序）

> 対象: MC の時間の単位。ゲームtick（1秒20回）とラグ、1日 24000 tick の昼夜の区切り、空の動きの速さ、tick の中での処理の順序、チャンクの tick、ランダムティック、予定 tick。`/tick` コマンドの詳しい使い方は別ファイル。
> 使う場面: すべての計測実験の設計（時間をどの単位で測るか）、台本で MC の1秒や MC の1日を説明するとき。
> 調査日: 2026-11-19 ／ mc_version: Java Edition 26.3（2026-11-19 時点の最新リリース [S5]）を前提にする。統合版（Bedrock）は違う点だけ書く。minecraft.wiki の記述は取得時点の版の説明とみなすが、各記述がどの版で確かめられたかは記事に書かれていない。
> 関連: [../filming/時間制御とスロー.md](../filming/時間制御とスロー.md)（`/tick` の詳細）, [レッドストーン信号.md](レッドストーン信号.md), [光.md](光.md), [世界の形と大きさ.md](世界の形と大きさ.md)（太陽と月の動き）

## 要点
- ゲームはふつう 1 秒に 20 tick の一定の速さで動き、1 tick は 0.05 秒（50 ミリ秒）。MC の1日はちょうど 24,000 tick（20 分）。【二次】[S1]
- パソコンの処理が追いつかないと 1 秒あたりの tick 数（TPS）が下がる。ほとんどの動作は実時間ではなく tick 数で決まっているので、遅いパソコンでは多くのことに時間がかかる。【二次】[S1]
- TPS を 20 に保てるのは、1 tick の計算にかかる時間（MSPT）が 50 ミリ秒以下のときだけ。Java では F3 のデバッグ画面に MSPT、F3+2 のグラフに TPS が出る（シングルプレイかマルチのホストのとき）。【二次】[S1]
- Java では `/tick` コマンド（1.20.3 の 23w43a で追加）で tick の速さを確かめたり操作したりできる。使い方は [../filming/時間制御とスロー.md](../filming/時間制御とスロー.md)。【二次】[S1]
- Java の1回のゲームループでは、関数（tick タグ）→ ディメンションごと（オーバーワールド → ネザー → エンド → カスタム）の処理、の順に進み、ディメンションの中では天候・時刻 → 予定されたブロックの tick → 流体の tick → チャンク（モブの湧き・ランダムティック）→ ブロックイベント → エンティティ → ブロックエンティティ、の順に処理される。【二次】[S1]
- ランダムティックは、16×16×16 のサブチャンクごとに毎 tick ランダムに選んだブロックに与えられる。Java では1サブチャンクあたりの数が `random_tick_speed`（既定 3）。【二次】[S1]
- Java の既定の設定で、あるブロックが次のランダムティックを受けるまでの時間の中央値は 47.30 秒、平均は 68.27 秒。1秒未満になる確率は 1.38%、5分を超える確率は 1.23%。【二次】[S1]
- 1.21.5（25w06a）から、完全に読み込まれたチャンクはプレイヤーが 8 チャンク以内にいなくてもランダムティックを受ける。【二次】[S1]
- 予定 tick（決まった時間後に起きる処理: リピーター、水の流れなど）は Java で1 tick あたり最大 65,536 個。統合版は1チャンクあたり1 tick に最大 100 個。【二次】[S1]
- 昼（0〜12000 tick）は 10 分、日の入り（12000〜13000）は 50 秒、夜（13000〜23000）は 8 分 20 秒、日の出（23000〜24000）は 50 秒。MC の時間は現実の 72 倍の速さ。【二次】[S2]
- 空（太陽・月・星）は一定の速さでは回らず、正午と真夜中に速く、日の出・日の入りのころに遅く動く。【二次】[S2]
- シングルプレイでゲームメニューを開いて一時停止すると昼夜のサイクルも止まる。マルチではサーバーが動いている限り進む。【二次】[S2]

## 詳細

### ゲームtick
ゲームのループが1回まわることを1ゲームtickと呼ぶ。【二次】[S1]
> 「The game normally runs at a fixed rate of 20 ticks per second, so one tick happens every 0.05 seconds (50 milliseconds or 1/20 seconds)」[S1]
> 「last exactly 24,000 ticks (20 minutes)」[S1]
> 「As the vast majority of actions are timed based on tick count rather than on real time, this means that many things take longer on a slower computer.」[S1]

MSPT（1 tick の計算に実際にかかったミリ秒）が 50 を超えると TPS は 20 を保てない。【二次】[S1]
> 「The TPS can be maintained at 20 only if the MSPT is no higher than 50.」[S1]

サーバーの重さの原因としてよく挙がるもの: ホッパー（上のアイテムを探し続ける）、レッドストーン部品（特にダスト。ブロック更新や光の更新が増える）、多数のモブの AI、高すぎるランダムティックの速さ。【二次】[S1]

Java では MSPT は F3 のデバッグ画面に ms ticks として出て、F3+2 のフレーム時間のグラフに TPS が出る。どちらも内蔵サーバーの値なので、シングルプレイかマルチのホストでしか見られない。【二次】[S1]

ゲームのコードや `/time`、`/tick` などのコマンドはゲームtickを単位にしている。レッドストーン tick（2 ゲームtick）はコミュニティの呼び方（詳しくは [レッドストーン信号.md](レッドストーン信号.md)）。【二次】[S3][S1]

昔の版との違い: 最初期の Cave game tech test では 1 秒 60 tick で動いていて、のちに（時期不明）1 秒 20 tick になった。【二次】[S1]
> 「The game runs at a fixed rate of 60 ticks a second」[S1]

### 1回のゲームループの処理の順序（Java）
記事の一覧を順番どおりに訳したもの。【二次】[S1]
1. 予定より 2 秒以上遅れていれば次の tick の時刻をリセットする
2. 次の tick の時刻を計算する
3. tick の数を1増やす
4. `tick` や `load` タグの付いた関数を実行する
5. 20 ゲームtick ごとにプレイヤーへ時刻を送る
6. ディメンションごとに、オーバーワールド → ネザー → エンド → カスタムディメンションの順で次を行う
   - ワールドボーダーの範囲を更新 → 天候を進める → 昼夜の時刻を更新 → 寝ているプレイヤーの処理 → `/schedule` のコマンドを実行
   - 予定されたブロックの tick → 予定された流体の tick → 襲撃の処理 → チャンクの読み込みレベルを更新
   - すべてのチャンクをランダムな順に: モブを湧かせる → 氷と雪の tick → ランダムティック
   - プレイヤーへブロックの変化を送る → POI を更新 → チャンクを読み込み解除 → ブロックイベントを実行 → ドラゴン戦の処理
   - 乗り物に乗っていないエンティティごとに: 消えるかの判定 → エンティティの tick → 乗っているエンティティの tick
   - ブロックエンティティの tick → ゲームイベントの処理
7. 各プレイヤーのパケットを送受信する → プレイヤーの情報を送る
8. 6000 tick ごとに自動保存する
9. 残りのタスクを実行し、次の tick を待つ

統合版の処理の順序は、記事では空欄になっている。【二次】[S1]

### チャンクの tick（Java）
エンティティが tick される読み込み状態のチャンクは毎 tick 処理される。主にシミュレーション距離の中のチャンクだが、ほかの方法で読み込まれたチャンクもランダムティックを受ける。モブの湧きと落雷には 8 チャンク以内のプレイヤーが必要で、降水にかかわる処理とほかのランダムティック（作物の成長など）にはプレイヤーは要らない。【二次】[S1]

チャンクの tick で起きること: モブの自然な湧き、雷雨中の落雷（1/100000 の確率）、1/16 の確率で1列を選んだ天候の判定（寒いバイオームで水が凍る、雪が積もる、大釜に水や粉雪がたまる）、ランダムティック。【二次】[S1]

> 「All fully-loaded chunks now receive random ticks, regardless of if a player is within an 8-chunk distance or not.」[S1]（1.21.5、25w06a）

1.20.2（23w31a）から、チャンクの tick の天候の判定の確率もランダムティックの速さのゲームルールの影響を受ける。【二次】[S1]

### ランダムティック
チャンクは高さ 16 ブロックごとのサブチャンク（16×16×16 = 4096 ブロック）に分かれ、チャンクの tick ごとに各サブチャンクからいくつかのブロックがランダムに選ばれてランダムティックを受ける。空気も含めてすべてのブロックが対象になりうる。【二次】[S1]
> 「Subchunks that do not contain at least one block that can react to random ticks are skipped.」[S1]

Java では1サブチャンクから選ぶ数がゲームルール `random_tick_speed`（記事の取得時点の表記。既定 3）で決まり、同じブロックが1回のチャンクの tick で複数回選ばれることもある。統合版の `randomTickSpeed`（既定 1）は相対的な速さを表すだけで、正確な数ではない。【二次】[S1]

ランダムティックで起きることの例: 作物の成長、キノコの広がり、ツタの伸び、氷・雪の融解、葉の消滅、耕地の水分の更新、サボテン・サトウキビ・竹・昆布などの成長、草ブロックと菌糸の広がり、苗木の成長、溶岩の延焼、光ったレッドストーン鉱石が消える、銅の酸化、アメジストの芽の成長。【二次】[S1]

ランダムなので次の tick の時刻は予測できない。Java の既定の設定で: 【二次】[S1]
> 「the median time between ticks is 47.30 seconds」[S1]
> 「On average, blocks are updated every 68.27 seconds」[S1]

平均の 68.27 秒は 4096/3 ≈ 1365.33 ゲームtick、中央値は log_{(4096−3)/4096}(0.5) ≈ 946.03 ゲームtick（幾何分布）。【二次】[S1]

ゲームルール `randomTickSpeed` は 1.8（14w17a）で追加された。【二次】[S1]

### 予定 tick（scheduled tick）
一部のブロックは、決まった時間後の tick を予約できる。Java のリピーターの状態変化や、水が流れるときに使われる。【二次】[S1]

Java の火の広がりと消え方は予定 tick で決まり（30〜40 ゲームtickごと）、ランダムティックの速さの影響を受けない。【二次】[S1]

> 「the maximum number of scheduled ticks per game tick is 65,536」[S1]

予定 tick の優先度と順序は [レッドストーン信号.md](レッドストーン信号.md) に書いた。【二次】[S1]

### 1日の時間（昼夜のサイクル）
昼夜のサイクルは 20 分の周期。【二次】[S2]
> 「is a 20-minute-long cycle」[S2]
> 「time is 72 times faster than normal time」[S2]

| 区間 | tick | 長さ（実時間） | 確度・出典 |
|---|---|---|---|
| 昼 | 0〜12000（6:00〜18:00、正午は 6000） | 10 分 | 【二次】[S2] |
| 日の入り | 12000〜13000 | 50 秒（1000 tick） | 【二次】[S2] |
| 夜 | 13000〜23000（真夜中は 18000） | 8 分 20 秒（10000 tick） | 【二次】[S2] |
| 日の出 | 23000〜24000 | 50 秒（1000 tick） | 【二次】[S2] |

> 「Daytime, not including sunset and sunrise, is 10 minutes long.」[S2]
> 「Sunset is the period between daytime and nighttime, and always lasts 50 seconds (1000 ticks).」[S2]
> 「Nighttime lasts 8 minutes and 20 seconds. (10000 ticks)」[S2]

単位の換算: MC の1時間 = 1000 tick = 実時間 50 秒、MC の1分 ≈ 16.67 tick（0.83 秒）、MC の1週間 = 168,000 tick（2時間20分）、月の満ち欠けの1周（8日）= 192,000 tick（2時間40分）。現実の1 tick は MC の 3.6 秒にあたる。【二次】[S2]

`/time set` の値（Java）: `/time set 0` で1日の始まり、`day` で 1000、`noon` で 6000、`12000` で日の入り。統合版の `sunrise` は 23000。【二次】[S2]
> 「Sets the time to 1000.」[S2]

昼夜のサイクルを止めるゲームルールは、取得時点の記事の表記で Java が `advance_time`、統合版が `dodaylightcycle`。もとの `doDaylightCycle` は 1.6.1（13w24a）で追加された。【二次】[S2]

### 空の動きの速さ
空の角度は時刻に比例せず、正午と真夜中に速く、日の出・日の入りに遅い。【二次】[S2]
> 「The sky, including sun, moon, and stars, move faster during noon and midnight and slower during sunrises and sunsets.」[S2]

記事の式（t は夜明けからの tick、0° が正午）: α = (1 − cos(π·mod₁((t−6000)/24000)) + mod₄((t−6000)/6000))·60°。【二次】[S2]

太陽と月と星は互いの位置が変わらないので日食は起きない。太陽と月は東から昇る（Beta 1.9 プレリリース4 までは北から昇るバグがあった）。どこでも同じかなどの話は [世界の形と大きさ.md](世界の形と大きさ.md)。【二次】[S2]

### 時間が止まる・進む条件
> 「The daylight cycle pauses when the game is paused in the」[S2]

プレイヤーがネザーやエンドにいる間も昼夜のサイクルは進む（オーバーワールドの世界はそれが読み込まれるまで変化しない）。【二次】[S2]

ベッドで寝て夜を飛ばすと、昼夜のサイクルは夜明けに進み天候は晴れになるが、ほかのものの時間は進まない（作物は育たず、かまどは精錬しない）。【二次】[S2]

### 時刻と内部の空の光（湧きの判定）
晴れのとき、空の光 15 の場所の内部の空の光は、23,961〜12,040 tick で 15、13,670〜22,330 tick で最低の 4。その間は約 160〜170 tick（約 8 秒）ごとに 1 ずつ変わる。【二次】[S4]

記事の時刻の表では、屋外で敵対モブが湧く最初の tick は晴れで 13188、雨で 12969、最後の tick は晴れで 22812（Java）、雨で 23031。時刻は、湧きの処理のあとに最初にコマンドが実行されたときの値で測ったと注記がある。【二次】[S2]

晴れの 13188〜22812 は、内部の空の光が 7 以下の区間（[S4] の表の 7 の始まり 13,188 と終わり 22,812）と一致する。【二次】[S2][S4]

同じ記事の本文には、湧ける時間の長さが 13188 tick だという記述がある。しかし 13188 は表では湧き始めの時刻で、表の値から自分で計算した長さ（22812 − 13188 + 1 = 9625 tick）と合わない。記事の中で食い違っているので、長さは【未確認】とする（下の「わかっていないこと」）。

光レベルの仕組みは [光.md](光.md)。

## このチャンネルでの使い方（提案）
> ※この節は上の事実から導いた提案で、事実ではない。
- 計測はすべて tick 数で記録し、秒への換算は 20 tick = 1 秒（TPS 20 のとき）であることを明示する。録画中に TPS が落ちると実時間と tick がずれるので、撮影中は F3 で MSPT が 50 未満かを確かめる。（根拠: [S1]）
- 動画内で MC の1秒を説明するときは、1 tick = 0.05 秒、つまり MC の物理は 1 秒に 20 コマのパラパラ漫画、という言い方ができる。コマ送りの撮影は `/tick freeze` と `/tick step` で行う（[../filming/時間制御とスロー.md](../filming/時間制御とスロー.md)）。（根拠: [S1]）
- ランダムティックを使う実験（作物の成長、氷の融解など）は、1回の観察では運に左右される（1秒未満も5分超もありうる）。多数のブロックを並べて平均を取るか、`random_tick_speed` を上げて時間を縮める（上げたことは動画で明示する）。（根拠: [S1]）
- 同じ tick の中の処理の順番（ブロックの tick → 流体 → エンティティ → ブロックエンティティ）は、実験で同時に見えることの順番を説明するのに使える。ただし記事の一覧は Java のもので、版による違いは未確認。（根拠: [S1]）
- 空の動きが一定でないことは、T13（エラトステネス）など太陽の角度を使う実験で注意が要る。時刻から角度を出すときは記事の式を使う。（根拠: [S2]）

## わかっていないこと・要確認
- 処理の順序の一覧 [S1] が Java 26.3 でもそのままか（記事に版の記載がない）。
- ゲームルールの名前が `random_tick_speed`・`advance_time` のような表記に変わったのがどの版か（今回の出典に記載がない）。撮影で使う版のコマンドで確かめる。
- 統合版の処理の順序（記事で空欄）。
- 晴れの夜に屋外で敵対モブが湧ける時間の長さ。記事 [S2] の本文は「The exact duration for which hostile mobs are able to spawn in exposed areas is 13188 ticks.」と書くが、同じ記事の表（最初 13188・最後 22812）から計算すると 9625 tick になり、食い違う。【未確認】
- TPS が 20 を下回ったとき、`/tick` の設定やエンティティの動きの計算が実時間とどうずれるか（[../filming/時間制御とスロー.md](../filming/時間制御とスロー.md) と合わせて確認）。
