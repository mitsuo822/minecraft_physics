# 時間制御とスローモーション

> 対象: ゲームの時間の進み方を変える方法。バニラの /tick（rate / freeze / step / sprint）の仕様と、止めている間に何が動くか、Carpet mod の tick 関連のコマンドの移り変わり、Replay Mod・Flashback の再生速度と時間のキーフレーム。それらを使ったスローモーションの撮り方の選択肢。
> 使う場面: 実験の計測方式を決めるとき（`lab/runner.py` の tick 送り）と、スロー・一時停止・早送りの撮影を計画するとき。
> 調査日: 2026-11-19 ／ mc_version: Java Edition。/tick は 1.20.3 以降（26.3 の snapshot での変更を含む）。Carpet の旧 /tick は 1.20.3 未満（Carpet TIS Addition の変更履歴の記述による）。Flashback 0.33.0 は 1.21.5 向けの版。統合版（Bedrock）は扱わない。
> 関連: [ワールド内の演出.md](ワールド内の演出.md), [ReplayMod.md](ReplayMod.md), [Flashback.md](Flashback.md), [カメラワーク技法.md](カメラワーク技法.md), [../mods/Carpet.md](../mods/Carpet.md), [../mods/バージョン対応表.md](../mods/バージョン対応表.md)

## 要点
- /tick は Java Edition 1.20.3 で追加されたバニラのコマンド（最初のスナップショット 23w43a は 2023-10-25 公開）。権限レベル 3 が必要で、既定ではコマンドブロックやデータパックからは使えない。【一次】[S2]【二次】[S1]
- /tick rate で目標の TPS を変えられる（wiki では 1.0〜10000.0、既定 20.0）。ゲームは既定の 20.0 TPS を前提にしたままなので、目標の TPS を変えるとゲームの相対的な速さが変わる。【二次】[S1]
- 20 未満にすると、プレイヤーの移動と入力も遅くなる。20 より上にしてもプレイヤーは 20 TPS のままで、エンティティの補間に乱れが出ることがある。【一次】[S2]
- /tick freeze は、プレイヤーとプレイヤーが乗っているエンティティ以外のすべてのゲーム要素を止める。止めた世界の中を自由に動いて調べられる。【一次】[S2]【二次】[S1]
- 凍結中でも、毎 tick の処理でないもの（ドアの開閉、レバー、レッドストーンダストへの信号の入り切り）は変わる。【二次】[S1]
- /tick step は凍結中だけ使え、指定した時間だけ進めて再び止める。時間は省略すると 1 tick（23w44a から）。d（24000 tick）・s（20 tick）・t の単位が使える。【二次】[S1]
- /tick sprint は目標の TPS を無視して全速で進める。wiki によると実際には指定した tick 数より 1 多く進む（wiki の脚注のバグ報告 MC-268324 は仕様どおり＝Works As Intended として閉じられた）。【二次】[S1]
- 26.3snap1 から、/tick step、/tick step stop、/tick sprint stop は失敗時にエラーを返すようになった（以前はメッセージを出して 0 を返すだけ）。【二次】[S1]
- Fabric の 1.20.3 向けの告知は、Carpet mod の /tick がバニラに入ったと書いている。【二次】[S10]
- 現在の Carpet の master のソースには /profile health と /profile entities がある。Carpet TIS Addition の変更履歴では /tick warp status の修正が 1.20.3 未満向けとされている。【一次】[S8][S9]
- Replay Mod の再生速度スライダーは 0.1〜8 倍。時間のキーフレームでリプレイ内の時刻を区間ごとに指定でき、同じ時刻のキーフレームを 2 つ置くとその区間は時間が止まる。カメラパスの中で時間を戻すことはできない。【一次】[S4]
- Flashback 0.33.0（Modrinth の表示では Java Edition 1.21.5 向け）から、時間以外のキーフレーム（カメラなど）の補間は tick ではなく実時間で進む。途中で再生速度を変えてもカメラの動きは速くも遅くもならない（設定で以前の方式に戻せる）。【一次】[S5]
- この調査で出典を確認できたスローの撮り方は、(1) /tick rate を下げて実時間で録る、(2) freeze と step でコマ送りする、(3) 普通の速さで録って Replay Mod・Flashback で遅く再生する、の3つ（下の表で整理）。【二次】[S1]【一次】[S2][S4][S5]

## 詳細

### /tick の書式（Java Edition 1.20.3 以降）
| サブコマンド | 内容（2026-11-19 取得時点の wiki と、23w43a の公式の変更履歴による） |
|---|---|
| `tick query` | 現在の状態と目標の TPS、tick あたりの処理時間の平均と百分位を表示する |
| `tick rate <rate>` | 目標の TPS を変える。既定 20.0 |
| `tick freeze` | プレイヤーと、プレイヤーが乗っているエンティティ以外を止める |
| `tick unfreeze` | 凍結を解く |
| `tick step [<time>]` | 凍結中だけ使える。指定した時間だけ進めて再び止める |
| `tick step stop` | 進めている途中で止めて、再び凍結する |
| `tick sprint [<time>]` | 目標の TPS を無視して全速で進める。終わると元の状態に戻り、その間の処理時間を表示する |
| `tick sprint stop` | sprint を止めて元の状態に戻す |

【二次】[S1]【一次】[S2]

- /tick はコマンドブロックからは実行できない。権限レベル 3。【二次】[S1]
> 「The /tick command cannot be executed from a command block.」[S1]
- 公式の変更履歴では、管理とデバッグ用のコマンドで、高い権限が必要なため既定ではコマンドブロックとデータパックで使えないとしている。【一次】[S2]
> 「The command requires elevated permissions (admins and above) and so it is not by default available in command blocks and datapacks.」[S2]
- rate の範囲: wiki は 1.0 以上 10000.0 以下（両端を含む）、公式の変更履歴は 1.0 より大きく 10000.0 より小さいと書いており、両端の扱いが食い違う。【二次】[S1]【一次】[S2]
- time の単位: d = 24000 tick、s = 20 tick、t = 1 tick（既定）。単位を換算したあと最も近い整数の tick に丸める（例: .5d は 12000 tick）。【二次】[S1]
> 「The time is set to the closest integer after unit conversion to gametick.」[S1]
- 履歴: 1.20.3（23w43a）で追加 → 23w44a で step の time が省略可能（既定 1）→ 1.20.3 pre3 で、処理が追いつかないとき query に「The game is running, but can't keep up with the target tick rate」と出るようになった → 26.3snap1 で step / step stop / sprint stop がエラーを返すようになった。【二次】[S1]
- 実行結果（/execute store で取れる値）: query と rate は目標の TPS、step stop と sprint stop は実行中だったかどうか（1 / 0）。【二次】[S1]

### tick rate を変えたときに何が変わるか
ゲームは 20 TPS を前提に動き続けるので、rate を変えるとゲームの相対的な速さが変わる。【二次】[S1]
> 「Modifying the target ticking rate changes the relative speed of the game as the game still expects a constant tick rate of 20.0, the default tick rate.」[S1]

20 未満にすると、プレイヤーの移動や入力も遅い頻度で処理される。20 より上にしたときはプレイヤーは 20 TPS のままだが、エンティティの補間に乱れが出ることがある。【一次】[S2]
> 「Setting a tick target lower than the default 20.0 will also cause the players to be simulated at a lower rate (including player movement and input controls)」[S2]
> 「setting a higher tick rate will cause the players to be simulated at the default rate of 20 ticks per second to maintain the expected responsiveness of the game, but can cause artifacts in entities interpolation.」[S2]

極端に低い rate はゲームの反応を悪くし、高すぎる rate はゲームが常に遅れていると見なしてクラッシュの原因になりうる。公式は tick query か、デバッグ画面の F3 + 2（内蔵サーバのみ）で処理の重さを測って調整するよう勧めている。【一次】[S2]
> 「Setting a very low tick rate can cause the game to feel unresponsive」[S2]

### freeze 中に何が動くか
- 止まらないのは、プレイヤーと、プレイヤーが乗っているエンティティ。【二次】[S1]【一次】[S2]
> 「All gameplay elements are not ticked, except players and any entity a player is riding.」[S1]
- 毎 tick 処理されるものではない操作は凍結の影響を受けない。wiki の例はドアの開閉、レバーの切り替え、レッドストーンダストの線への信号の入り切り。【二次】[S1]
> 「Game aspects that are not processed periodically every tick are unaffected; a few examples: opening or closing a door, flicking a lever, powering or depowering redstone dust lines.」[S1]
- 公式は freeze の用途を、プレイヤーが自由に動き回って世界を調べられるデバッグ用と説明している。【一次】[S2]
> 「This is useful for debugging and isolating issues with the game allowing the player to move around freely and inspect the world.」[S2]
- 凍結や一時停止と描画の関係についてのバグ報告（MC-266656 など）は、原文を読めていないので「わかっていないこと・要確認」に書いた。

### 表示エンティティの補間と tick
表示エンティティの補間の長さ（interpolation_duration、teleport_duration）は tick 単位で指定し、サーバは状態を 1 tick に最大 1 回しか送らない。詳しくは [ワールド内の演出.md](ワールド内の演出.md)。【二次】[S3]
> 「Since server synchronizes entities with the client at most once per game tick, multiple changes within one game tick still count as a single change.」[S3]

### Carpet mod の tick 関連（古いバージョンとの違い）
- Carpet は Modrinth の表示（2026-11-19 取得）で、Java Edition 26.3、26.2、26.1.x、1.21.x、1.20.x … 1.14.4 に対応する Fabric の mod で、ライセンスは MIT。【一次】[S7]
- 現在の Carpet のソース（GitHub の master）には `/profile` があり、`/profile health [ticks]` と `/profile entities [ticks]`（ticks は 20〜24000、省略時 100）で処理の重さを報告する。使えるかどうかは Carpet の設定 commandProfile で決まる。【一次】[S8]
- Carpet の拡張 Carpet TIS Addition の変更履歴（v1.54.2、mc1.20.3-rc1 向け）には、1.20.3 未満向けの /tick warp status の修正と、1.20.3 向けの新しいルール tickProfilerCommandsReintroduced の追加が書かれている。1.20.3 未満の環境に /tick warp（少なくとも Carpet TIS Addition が扱う /tick warp status）があったことを示す記述で、Carpet 本体の /tick の仕様そのものは書かれていない。【一次】[S9]
> 「(<mc1.20.3) Fixed /tick warp status command becomes inaccessible since v1.52.0」[S9]
> 「(1.20.3) Added rule tickProfilerCommandsReintroduced」[S9]
- Fabric の Minecraft 1.20.3 / 1.20.4 向けの告知（2023-11-30）は、mod 開発者向けに、Carpet mod の /tick がバニラに入り、サーバとクライアントの両方に影響すると書いている。意図的に 50 MSPT より速く・遅く動かせるようになったので、mod は TickManager#getMillisPerTick() で意図した MSPT を調べる。【二次】[S10]
> 「The `/tick` command from the Carpet mod arrived in the vanilla game. This change affects both the server and the client.」[S10]
- gnembon の文書（Carpet の /tick とバニラの /tick の違い）と、Carpet TIS Addition のルール tickCommandCarpetfied の説明は、検索要約しか得られていないので「わかっていないこと・要確認」に書いた。

### Replay Mod の再生速度と時間のキーフレーム
- 再生・一時停止ボタンの横の速度スライダーで、リプレイ内の時間の進む速さを変えられる。最小は通常の 0.1 倍、最大は 8 倍。【一次】[S4]
> 「The minimum Speed value is 0.1 times the normal Minecraft Tick Speed, and the maximum Speed is 8 times as fast.」[S4]
- キーフレームのタイムラインは 10 分の長さで、その時刻はリプレイ内の時刻ではなく実時間（できあがる映像の時間）を表す。【一次】[S4]
> 「Other than the Replay Timeline, the Keyframe Timeline's time values are not relative to the Replay's point of time, but refer to real time.」[S4]
- 時間のキーフレーム（Time Keyframe）はそれぞれリプレイ内の時刻を持ち、カメラパスの再生中、リプレイの時刻はキーフレームの間で補間される。同じ時刻のキーフレームを 2 つ置くと、その区間はリプレイの時間が止まる。【一次】[S4]
> 「Two Time Keyframes with the same Timestamp will freeze the Replay time for the duration of their interval.」[S4]
- カメラパスの中で時間を戻すことはできない（前のキーフレームより早い時刻のキーフレームを後ろに置かない）。【一次】[S4]
> 「Travelling backwards in time is not supported during Camera Paths.」[S4]
- V キーで、速度スライダーの今の値になる位置にタイムラインのカーソルを合わせられる（Shift を押しながらだと 1.0 倍として合わせる）。【一次】[S4]
- カメラの経路の補間は既定で 3 次スプライン。設定か O キーで直線に切り替えられる。【一次】[S4]
- 相性の問題として、Tickrate Changer mod を入れているとリプレイの画面で固まることがある。【一次】[S4]
> 「The Tickrate Changer mod may cause minecraft to freeze when you try to use the Replay Viewer UI.」[S4]
- Replay Mod の機能・対応バージョン・レンダリング設定は [ReplayMod.md](ReplayMod.md) を見る。

### Flashback の再生速度
- Flashback の Modrinth の対応表示（2026-11-19 取得）は Java Edition 26.3、26.2、26.1.x、1.21.4〜1.21.11、1.21〜1.21.1。1.20.x は表示されていない。【一次】[S6]
- 0.33.0（Modrinth の表示では MC Java Edition 1.21.5 向け、Modrinth の相対表示「昨年」から 2025 年公開）から、時間以外のキーフレームの補間は tick ではなく実時間で進む。カメラの動きの途中でリプレイの速度を変えても、カメラの動き自体は速くも遅くもならない。以前の tick 基準の補間は設定（Preferences）で戻せる。【一次】[S5]
> 「Interpolation for non-time keyframes now uses realtime instead of ticks」[S5]
> 「if you modify the speed of the replay in the middle of a camera movement, the camera movement itself won't speed up or slow down」[S5]
> 「The old tick-based interpolation can be reenabled in the Preferences window」[S5]
- 同じ版で、リプレイを一時停止している間にクリエイティブで変えたブロックが残るようになった（Block Overrides のキーフレームとして記録される）。【一次】[S5]
> 「Block changes that occur in creative mode while the replay is paused now persist」[S5]
- Flashback のキーフレームの種類（速度・タイムラプスなど）は、変更履歴の一覧ページの本文が取れず確認できていない（「わかっていないこと・要確認」に書いた）。機能の全体は [Flashback.md](Flashback.md) を見る。

### スローモーションの撮り方の選択肢（事実の整理）
| 方式 | わかっていること | 出典 |
|---|---|---|
| /tick rate を下げて実時間で録る | ゲーム全体が遅くなる。プレイヤーの移動と入力も遅い頻度で処理される | 【一次】[S2]【二次】[S1] |
| /tick freeze + step でコマ送り | 指定した tick だけ進めて止まる。凍結中もプレイヤーは動ける | 【一次】[S2]【二次】[S1] |

| 普通の速さで録り、Flashback で遅く再生 | 0.33.0 以降、速度を変えてもカメラの動きは実時間で進む | 【一次】[S5] |

## このチャンネルでの使い方（提案）
> ※この節は上の事実から導いた提案で、事実ではない。

- **スローは、普通の 20 TPS で実験して録画 mod で遅く再生する方式を基本にする。** tick rate を下げると、カメラ役のプレイヤーの動きと入力まで遅くなるため（根拠: [S2]）。リプレイなら実験そのものは通常の速さのままなので、計測の条件と撮影の条件がそろう（根拠: [S1][S4][S5]）。
- **0.1 倍のスローはコマ数に注意する。** 0.1 倍だと 1 tick（50 ms）が実時間 0.5 秒になり、60 fps なら 1 tick あたり 30 コマになる（上の数値からの計算）。その 30 コマの間に物体がなめらかに動いて見えるかは、クライアントの補間しだいで、ここでは確認できていない。T 系の落下・衝突の回で、0.1 倍・0.25 倍・0.5 倍を書き出して比べ、【実測】にする（根拠: [S4]、要確認の項目）。
- **バレットタイム（止めた世界をカメラが回り込む）は /tick freeze で撮れる可能性がある。** 凍結中もプレイヤーは動けるので、スペクテイターのカメラで回り込める（根拠: [S1][S2]）。ただし描画の位置ずれのバグ報告があるという検索要約がある（根拠: [S13][S14]。原文未読・【未確認】）ので、1.20.3 以降の基盤バージョンで試撮りしてから台本に入れる。リプレイ側なら Replay Mod の同じ時刻の時間キーフレーム2つで止めるほうが確実（根拠: [S4]）。
- **計測（`lab/runner.py`）は今の方式（RCON で freeze → step 1）でよい。** /tick は既定ではデータパックやコマンドブロックから使えないので、外から操作する方式が合っている（根拠: [S1][S2]）。基盤を 26.3 以降にする場合は、step の失敗がエラーとして返るので、runner の失敗の判定をその前提で書く（根拠: [S1]）。
- **凍結中に装置を準備するときは、レバー・ドア・レッドストーンダストの状態が止まらずに変わることを前提にする。** 止めてからスイッチを入れて step で始める手順は、スイッチの段階で一部が動いてしまう可能性がある（根拠: [S1]）。どこまで動くかは E001 の手順で【実測】する。
- **待ち時間は /tick sprint で飛ばす。** 装置が落ち着くまでの待ちなどに使える。ただし指定より 1 tick 多く進むので、tick 数を正確に数える計測の区間では使わない（根拠: [S1]）。
- **Carpet の旧 /tick（warp、freeze の切り替え）の解説や手順を見たら、1.20.2 以前の情報として読み替える。** 処理の重さを見るのは Carpet の /profile health、時間の操作はバニラの /tick を使う（根拠: [S8][S9]、[S11] は原文未読）。
- **Flashback を使う場合は基盤を 1.21 以降にする。** 1.20.x の対応が表示されていないため（根拠: [S6]）。どのバージョンにするかは [../mods/バージョン対応表.md](../mods/バージョン対応表.md) で決める。
